# extend_disk

Ansible-роль для расширения ext4/XFS и явно выбранного FAT32 после увеличения виртуального диска,
например в vCenter. На системном диске расширяется `/`; на дополнительном
диске — единственный раздел или единственный обычный linear LV. Явная точка
монтирования позволяет выбрать другой раздел/LV и распределить место между LV.

Роль не создаёт разделы, PV, VG, LV или файловые системы и не переносит данные.

## Использование

Поместите репозиторий в `roles/extend_disk`:

```yaml
- hosts: servers
  become: true
  gather_facts: true
  roles:
    - role: extend_disk
      extend_disk_dry_run: true
```

Сначала запустите с `extend_disk_dry_run: true`, затем для применения установите
`false`. При необходимости ограничьте список дисков:

```yaml
extend_disk_devices:
  - /dev/sda
  - /dev/sdb
```

Пустой список означает автоматический выбор поддерживаемых дисков. Неизвестный
путь в явном списке — ошибка. Можно использовать `/dev/disk/by-id/...`:
скрипт разрешает ссылки перед проверкой выбора.

## Выбор точки монтирования и распределение места

Новое поле по умолчанию пустое:

```yaml
extend_disk_mountpoints: ""
```

В нём можно перечислить **точные точки монтирования** через пробел или запятую:

```yaml
extend_disk_mountpoints: "/second_data, /var"
```

На диске с явно указанной целью она заменяет автоматический выбор. Например,
`/var` на системном диске выбирает `/var` вместо `/`. На остальных дисках
автоматика сохраняется: если `/second_data` находится на дополнительном диске,
системный `/` продолжает расширяться по умолчанию. Явный выбор нескольких целей
на одном диске разрешён; для нескольких LV одной VG требуется распределение.

Если на дополнительном диске несколько возможных целей и ни одна не выбрана,
он пропускается с подсказкой `extend_disk_mountpoints` и найденными точками
монтирования. Остальные диски обрабатываются. Опечатка, путь внутри файловой
системы вместо точки монтирования или конфликт с `extend_disk_devices` — ошибка.

Для LVM поддерживаются три формы:

| Запись | Значение |
| --- | --- |
| `/data=20GiB` | Добавить 20 GiB к выбранному LV |
| `/data=40%` | Добавить 40% свободного места его VG после расширения PV |
| `/data` | Отдать этому LV оставшееся свободное место его VG |

Примеры для нескольких LV **одной VG**:

```yaml
# Добавить 20 GiB к /data, остальное отдать /logs.
extend_disk_mountpoints: "/data=20GiB, /logs"
```

```yaml
# Распределить свободное место в пропорции 40/60.
extend_disk_mountpoints: "/data=40% /logs=60%"
```

```yaml
# 25% отдать /data, 20 GiB — /logs, остаток — /archive.
extend_disk_mountpoints: "/data=25%, /logs=20GiB, /archive"
```

Размер **добавляется**, а не задаёт конечный размер LV. Знаки `+` и слово `rest`
не используются. Поддерживаются `B`, `KB`, `MB`, `GB`, `TB` (степени 1000) и
`KiB`, `MiB`, `GiB`, `TiB` (степени 1024). Регистр любой: `b`, `kb`, `mb`, `gb`,
`tb`, `gib`, `GiB` и т. п. Например, `1GB` = 1 000 000 000 байт, `1GiB` =
1 073 741 824 байта. Размеры и проценты могут быть дробными, но размер должен
выражать целое число байт. Пробелы допускаются между записями, не вокруг `=`.

Все проценты одной VG считаются от **одного общего объёма** свободного места
после расширения PV, до первого `lvextend`. Порядок перечисления не влияет на
распределение. Учитывается и место, уже свободное в VG до запуска. В разных VG
расчёты независимы: в каждой может быть свой путь без размера.

В одной VG допускается один получатель остатка. Два пути без размера, сумма
процентов больше 100% или запрос больше доступного объёма отклоняются при
предварительной проверке, до изменения разделов/PV/LV. Если свободного места
совсем нет, корректные запросы размеров тоже получают `SKIP`, без ошибки CI.
Если место есть, но его недостаточно для запрошенного объёма, будет ошибка.

Размер округляется вверх до LVM extent, доли — вниз; при сумме ровно 100%
оставшиеся extents распределяются по наибольшим дробным остаткам. Без получателя
остатка незапрошенное место остаётся в VG. Перед изменением LV расчёт повторяется
по фактическому размеру PV; ошибки ядра/LVM не превращаются в успешный `SKIP`.

**Повторный запуск с размером или неполными процентами снова запрашивает
добавление**, если в VG осталось место. Это не постоянный целевой размер.
После частичного сбоя проверьте итоговые размеры и скорректируйте запрос.
При необходимости завершите расширение FS штатными `resize2fs`/`xfs_growfs`.
Если весь свободный объём был распределён, повторный запуск ничего не добавит
и проверит FS.

Для обычных ext4/XFS-разделов доступна только запись без размера: весь доступный
смежный промежуток. Для FAT32 также доступен добавляемый размер, см. ниже.
Роль не перемещает соседние разделы. Для нескольких LV всё ещё
требуется VG с одним PV; multi-PV VG остаётся неподдерживаемой.

## EFI / FAT32: отдельный офлайн-режим

FAT32 нельзя расширить онлайн средствами этой роли. Для явно выбранного
FAT32-раздела GPT с типом EFI System или Microsoft Basic Data добавлен режим
с временным размонтированием:

```yaml
extend_disk_mountpoints: "/boot/efi=128mb"
extend_disk_allow_unmount: true
```

Он добавит примерно 128 000 000 байт к разделу/FS, **если непосредственно после
раздела есть свободное место**. Округление FAT/раздела выполняет `fatresize`.
Без размера (`"/boot/efi"`) используется весь смежный свободный промежуток.
Проценты поддерживаются только для LVM. `=1GiB` означает **добавить** 1 GiB,
а не получить конечный размер 1 GiB.

По умолчанию `extend_disk_allow_unmount: false`. При наличии места и необходимости
офлайн-расширения запуск без разрешения завершается понятной ошибкой до изменения
разметки. Dry-run показывает план без размонтирования и без этого разрешения.
При отсутствии пригодного места получается успешный `SKIP`, разрешение не нужно.
FAT не выбирается автоматически и не поддерживается внутри LV или bind mount.
FAT12/FAT16, FAT на MBR, exFAT и NTFS не включены в этот режим.

При включённом параметре роль устанавливает `dosfstools` и `fatresize`
(`extend_disk_fat_packages` можно переопределить). Они должны быть доступны в
репозиториях конкретной ОС; для обычного запуска эти пакеты не требуются.

Перед изменением выполняется обычный `umount`; занятая FS вызывает ошибку,
принудительное/lazy размонтирование не применяется. `fsck.fat -n` проверяет FS
без исправлений. Затем `fatresize` расширяет раздел и FAT32, проверяются UUID,
тип, начало и остальные записи разделов, FAT volume ID, размер в ядре и FS.
Роль пытается восстановить исходное монтирование с прежними опциями и при ошибке.
Неудача восстановления возвращает ошибку, а не успешный результат.

**Смежное место обязательно.** Например:

```text
sda1  /boot/efi  600 MiB
sda2  /boot        1 GiB   ← начинается сразу после sda1
sda3  LVM
```

Увеличение диска в виртуализации добавит место после последнего раздела.
Роль не сможет передать его `/boot/efi` через `/boot` и LVM и выдаст `SKIP`.
Для такой разметки нужна отдельная офлайн-переразметка/миграция, а не включение
`extend_disk_allow_unmount`. Включать этот параметр без смежного места бесполезно.

`extend_disk_dry_run` запрещает rescan и изменение блочных устройств;
установка пакетов и копирование helper-файла Ansible при этом выполняются.
Он показывает возможность расширения раздела и состояние LVM, а не обещает,
что каждый найденный filesystem обязательно увеличится. Если ядро ещё не видит
новый размер диска из vCenter, dry-run его не обнаружит. Обычный запуск делает
rescan существующих выбранных устройств перед повторным чтением размеров.

Ansible `--check` проверяет установку/копирование, но пропускает запуск helper:
на первом запуске файл ещё может отсутствовать, а на повторном — быть старым.
Для проверки самих дисков используйте `extend_disk_dry_run: true` без `--check`.

Helper можно запускать отдельно:

```sh
sudo python3 files/extend_free_space.py --dry-run
sudo python3 files/extend_free_space.py --disk /dev/sda --disk /dev/sdb
sudo python3 files/extend_free_space.py --mountpoints '/data=20GiB, /logs' --dry-run
```

## Как принимается решение

1. `lsblk` и `findmnt` определяют `/`, физические диски и цепочки хранения.
   Поддерживается старый `lsblk` с `MOUNTPOINT` вместо `MOUNTPOINTS`.
2. Для LVM до изменения разделов проверяются метаданные PV/VG и **все** сегменты LV.
3. `growpart --dry-run` проверяет реальную разметку и доступное смежное место.
   Размер раздела не вычитается из размера диска, номера разделов не считаются
   их физическим порядком.
4. Для ext4/XFS `growpart` расширяет раздел и обновляет его размер в ядре. Затем helper
   сравнивает размер из таблицы `sfdisk --json` с `blockdev`. Если ядро всё ещё
   видит старый размер, обработка этого устройства останавливается с ошибкой.
5. Для LVM выполняются `pvresize`, затем `lvextend` с точным числом свободных
   extents и явным PV. `+100%FREE` для всей VG не используется.
6. `resize2fs` или `xfs_growfs -d` расширяет ext4/XFS. Её геометрия
   проверяется до/после; `CHANGED:` печатается при подтверждённом изменении.

Перенос резервного GPT-заголовка после увеличения диска обрабатывает `growpart`
через штатные средства разметки. Интерактивного `Fix/Ignore` или слепой отправки
`Yes` в `parted` больше нет. Ошибки чтения GPT не принимаются за отсутствие места.
FAT32 использует отдельную ветку `fatresize`, описанную выше.

## Повторный запуск и LVM

Повторный запуск не зависит от наличия свободного хвоста: если раздел или LV
уже вырос, а файловая система — ещё нет, роль завершает её расширение.
Если таблица уже записана, но размер раздела в ядре остался старым, выполняется
адресный `partx --update`; при неудаче потребуется перезагрузка и новый запуск.
Уже выполненное расширение раздела/PV/LV не откатывается.

На системном диске могут быть `/boot`, EFI и несколько LV: автоматическая цель — `/`.
Свободное место **одного PV этой VG**, включая существовавшее до запуска,
отдаётся корневому LV. На дополнительных дисках автоматически выбирается только
один LV; для нескольких нужно указать цели/распределение в `extend_disk_mountpoints`.

Multi-PV VG, thin/RAID/striped/snapshot LV отклоняются до изменения их раздела.
Это намеренное ограничение: для таких схем нужна явная политика распределения,
а прежний `+100%FREE` мог расходовать место других дисков. Раздел, за которым
расположен другой раздел, может расти лишь до его начала; свободный хвост за
`swap` нельзя добавить к корню без изменения разметки.

Не поддерживаются LUKS, mdraid, multipath, Btrfs и несмонтированный XFS.
Для дополнительного диска с несколькими разделами требуется явный выбор.
ext4 может быть смонтирован или не смонтирован;
для offline ext4 штатный `resize2fs` может потребовать предварительный `e2fsck`.
Роль не выполняет исправление файловых систем автоматически.

Одновременные изменяющие запуски helper блокируются через `flock`. Ошибка одного
устройства не скрывает остальные результаты; итоговый код возврата будет ненулевым.

## Пакеты и совместимость

Нужны Linux, Python **3.7+**, `lsblk`, `findmnt`, `blockdev`, `sfdisk --json`,
`growpart`, `partx`, `udevadm`, LVM2 с JSON-отчётами, e2fsprogs и xfsprogs.
Пакеты выбираются по менеджеру пакетов, а не названию дистрибутива:

| Системы | Менеджер | Пакет growpart |
| --- | --- | --- |
| Debian / Astra | apt | cloud-guest-utils |
| RED OS | dnf / yum | cloud-utils-growpart |

Списки находятся в `defaults/main.yml`. `sfdisk` поставляется через зависимости
`cloud-guest-utils` либо через `util-linux`; это учитывает разделение пакетов в
разных версиях Debian/Astra. Для локального репозитория списки можно
переопределить через `extend_disk_packages`. `extend_disk_packages: []`
пропускает установку, если зависимости уже подготовлены.

Проверки выполнены на Debian 13; конкретные версии RED OS/Astra требуют прогона
на тестовой VM с их пакетами. Наличие ветки apt/yum само по себе не подтверждает
совместимость со всеми версиями этих ОС.

## Проверки

```sh
python3 -m unittest discover -s tests -v
python3 tests/check_role.py
ansible-playbook -i localhost, tests/role.yml --syntax-check
ansible-playbook -i localhost, tests/role.yml --check
```

Тесты на временных обычных файлах запускают настоящие `growpart`, `sfdisk`,
`mkfs.ext4`, `resize2fs` и проверяют GPT после увеличения диска, MBR, сохранение
UUID/начала/соседних разделов, физический порядок разделов и повторный запуск.
Для них не нужны root, loop-устройства и mount. Если утилиты не установлены,
соответствующие тесты явно помечаются skipped.

Остальные тесты проверяют выбор root/data, ограничения LVM, порядок PV/LV/FS,
повторный запуск после частичного успеха и остановку при старом размере в ядре.

Результаты проверки и реальные прогоны в VM: [tests/VALIDATION.md](tests/VALIDATION.md).

Каноническая структура роли: `defaults/`, `tasks/`, `files/`. Старые верхнеуровневые
`main.yml`, `main (1).yml`, `extend_free_space.py` оставлены ссылками для совместимости.
